# Diagnosing a slow query

1. Find the statement in the slow-query log. Group identical statements and look at count and duration.
2. Get the execution plan (`EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL). Warning signs: `Seq Scan` on a large
   table with a high "Rows Removed by Filter", a `Sort` that an index could have provided, nested loops with a
   high loop count.
3. List the indexes on the tables involved. Check that the columns in WHERE and ORDER BY are covered, in that order.
4. Check whether the predicate can use an index at all: a function around the column (`lower(email)`,
   `date(created_at)`) or a leading wildcard (`LIKE '%abc'`) prevents it.
5. Compare with the plan from before the regression if one was saved, and with the list of recent migrations.
6. Check the application for N+1 patterns: one query per row of a previous result.
7. Propose the smallest safe change and say how to verify it (plan after the change, latency after the change).
